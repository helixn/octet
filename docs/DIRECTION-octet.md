# Направление: octet (PoW-криптовалюта Octet / OctetHash)

Направление для проекта Octet (github.com/helixn/octet): PoW-алгоритм OctetHash
на CUDA, reference-реализация на Python (оракул корректности), будущая нода на
Rust, постквантовая криптография (ML-DSA/SLH-DSA/ML-KEM).

## Нерушимые правила направления
1. **Reference — оракул.** `reference/octet_ref.py` — исполняемая спека. Любая
   CUDA/Rust реализация обязана давать байт-в-байт те же результаты, что
   reference на векторах. Расхождение = баг реализации, не «особенность GPU».
2. **Спека заморожена до правок.** Изменение параметров/структуры OctetHash —
   только через скил `pow-spec-review` и новую версию vN+1 в `docs/pow.md`
   (протокол: старая версия остаётся в истории, тест-векторы регенерируются).
3. **Криптография без Shor-уязвимых примитивов**: никаких ECDSA/EdDSA/RingCT/
   ECC-SNARK в консенсусе. Только ML-DSA / SLH-DSA / ML-KEM / BLAKE2b.
   Изменения криптографии — только через `pq-crypto-review`.
4. **Ворота качества не обходятся**: зелёный pytest ≠ сдача; DoD см. ниже.
5. **Секреты**: ключи GitHub/данные кошельков в логи и в тесты не пишутся
   (Zero Auth Leak, CWE-532); тест-векторы — только синтетические.

## Definition of Done (ворота направления)
```bash
python -m pytest tests/ -q          # reference-оракул: все векторы зелёные
scripts/dod_cuda.bat (Windows) / make -C cuda compile-only (Linux/CI)
# Фаза 1+ добавляется автоматически при появлении ноды:
# cargo clippy --workspace -- -D warnings && cargo test --workspace
```

## Порядок скилов
1. `investigate-codebase` — карта репо (reference / cuda / docs / future node).
2. Задача по спеке PoW → `pow-spec-review` (параметры меняются только тут).
3. Задача по GPU-солверу → `cuda-kernel-dev` (векторы ДО кода, бит-в-байт сверка).
4. Любое касание криптографии/приватности → `pq-crypto-review`.
5. Фича по спеке или крупный объём → конвейер `pipeline` (Coder → Reviewer →
   Gate-панель 2/3) — обязателен для всего, что попадает в консенсус.

## Специфика против web-fastapi
Здесь нет HTTP-контрактов и миграций БД. Главные риски другие: **расхождение
GPU-реализации с reference** (тихая порча консенсуса), **ошибка в криптографии**
(необратима после генезиса) и **подгонка параметров под бенчмарк** (спека
заморожена, бенч не может менять параметры). Поэтому «маятник миграций» заменён
бит-в-байт сверкой с reference, а фичи консенсуса всегда идут через pipeline.
